3. METHODE DE TRAVAIL (A RESPECTER)
-----------------------------------

Cycle d'un lot :
  1. Branche feat/<nom> depuis master (master propre et egal a origin/master).
  2. Test ROUGE d'abord, sur une assertion (jamais sur une erreur de syntaxe ou un import manquant).
  3. Implementation minimale.
  4. Mutation de controle d'une ligne : le test DOIT passer au rouge. Si le test reste vert, l'assertion est trop grossiere : ajouter un cas limite (exemple vecu : abaisser le seuil de contraste 4,5 a 3,0 restait vert tant qu'aucun cas n'etait entre 3 et 4,5).
  5. Restauration (vert), Pint, Larastan, Pest complet.
  6. Commit, push (le hook rejoue tout), fusion en merge commit (--no-ff, jamais squash), push de master, verification master == origin/master, ALORS SEULEMENT tag stable-AAAA-MM-JJ-<lot>, push du tag, suppression de la branche locale.

Regles Git : git add fichier par fichier, jamais git add . ; pas de --no-verify ; le hook ne controle pas les tags (un tag pousse a tort sur un commit rouge a deja du etre supprime).

Hooks Husky :
  pre-commit : lint PHP des fichiers modifies.
  pre-push : Pint --test, Larastan, npm run test:js, Pest complet en parallele. Un push de suppression de branche ou de tag saute les verifications.

Tests Pest : helpers communs dans tests/Pest.php (adminUser(), publicationUser(), setDeleteCode()). Les fonctions declarees dans un fichier de test sont GLOBALES : prefixer chaque helper (exemples : spa* dans ThemeStatusPaletteTest, cs* dans ThemeClairSombreTest, mro*, dsql*, dcnt*) ; ne jamais nommer un helper visit() (reserve par Pest). Les constantes globales de test aussi (CS_ROLES, SPA_FAMILIES...).
Dossier : un test qui appelle config(), view() ou la base doit etre dans tests/Feature (le dossier Unit ne demarre pas l'application ; Pest.php lie TestCase a Feature seulement). Un test Unit qui a besoin de la config lit le fichier : (require dirname(__DIR__, 2).'/config/themes.php')['themes'].
Tests JS : node --test sans dependance, via "npm run test:js" (liste de fichiers dans package.json : l'ajouter a chaque nouveau fichier .test.js). Logique pure dans resources/js/**/xxx-lib.js, branchement DOM minimal dans le fichier appelant.
Accents : dans les fichiers PHP, sequences \u{e9} ou entites HTML (PowerShell 5 abime l'affichage). Commits sans accents.
Scripts d'edition cote Windows : un seul bloc "& { ... }" colle d'un coup, ancre comptee (refus si le nombre d'occurrences differe de 1), idempotents, UTF-8 sans BOM, detection CRLF/LF, mutation dans try/finally qui restaure le fichier.
Avant le Pest complet sous Windows : TEMP et TMP vers storage\framework\tmp, puis php artisan view:clear (restaurer ensuite).

5. SYSTEME DE THEMES (lots 3d a 3e-3) - LE PLUS RECENT
-------------------------------------------------------

5.1 Principe : tout part de "roles de couleur" resolus par couches, emis en variables CSS dans <style> de <x-theme-style/> (App\View\Components\ThemeStyle, vue components/theme-style.blade.php, presente dans les layouts public et admin).
  Couches, la derniere l'emporte (ThemeStyleBuilder::css(?primary, ?secondary, ?theme, ?customColors) et ThemePalette::resolve) :
    1. defauts de ThemeRoles
    2. reglages historiques site_settings.primary_color et secondary_color
    3. palette du theme choisi (config/themes.php, colonne site_settings.theme, defaut 'cidst')
    4. couleurs personnalisees site_settings.theme_colors (JSON, Super Admin, page Reglages)
  Une valeur invalide (pas #RRGGBB) ou un role inconnu est ignore. Les couleurs personnalisees ne touchent JAMAIS aux etats (danger, success, warning) ni a la coque admin (admin_*) : seules les palettes de config/themes.php le peuvent.

5.2 Roles : primary, secondary, accent, bg, surface, text, muted, border (+ primary_content, secondary_content, accent_content, couleur du texte pose dessus).
  Variables emises : --color-<role>-rgb (triplet "R G B" sans virgule, utilise par tailwind.tokens.js), + variables DaisyUI.
  Etats (ThemeRoles::statusDefaults() / statusVariable()) : danger, success, warning, chacun en base, -soft (fond doux) et -content (texte sur fond doux) ; valeurs par defaut dans :root de resources/css/shared.css (faites pour fond clair).
  Fichiers : app/Services/Theme/{ThemeRoles, ThemePalette, ThemeStyleBuilder, ColorConverter, ContrastChecker, ContrastGuard}.php ; config/themes.php ; resources/css/shared.css ; tailwind.tokens.js ; tailwind.config.js (DaisyUI + couleurs admin.*).
  ContrastGuard : garde-fou de lisibilite des couleurs saisies dans les Reglages (bloque texte principal < 4,5 sur bg ou surface ; avertit seulement pour le reste). Le texte sur primaire est calcule (ContrastChecker::readableTextOn), jamais saisi.

9. PIEGES CONNUS
----------------

  - PowerShell : deux commandes collees sans saut de ligne se fondent en une ; un seul bloc par collage, puis une Entree de plus ; ne jamais coller de sortie de tests dans PowerShell.
  - Windows "rename ... storage\framework\views ... Acces refuse (code 5)" : verrou antivirus/indexeur, sans lien avec le code. Exclure le dossier storage dans Windows Security, php artisan view:clear puis view:cache. Cause probable des durees de Pest tres variables (150 a 530 s).
  - Un git commit oublie laisse les fichiers en M/A : verifier git log et git status avant de pousser.
  - Un patch applique avec "git apply" sur Windows : utiliser --ignore-whitespace (fins de ligne CRLF/LF).
  - En .NET/PowerShell, StartsWith(string) est culturel : utiliser StringComparison.Ordinal.
